## Incident — server unreachable, root filesystem went read-only (2026-11-01)

**Symptom (≈18:10).** `https://192.168.1.169:8006` timed out in Chrome and Edge.
Ping answered; a TCP connect to 8006 sometimes succeeded; `curl.exe -v` connected
but the TLS handshake never got a reply; SSH connected then closed immediately.

**Ruled out along the way:** VPN on the desktop (off, still failed), Chrome
extensions (Edge failed too), missing `https://`, IP conflict (ARP showed an MSI
MAC, `30-9c-23-…` — steel's board — consistently, also with the work laptop off),
desktop state (rebooted), Ethernet cable (`ping -n 100`: 1% loss, Wi-Fi-typical
spikes — can't explain a 100% browser failure).

**Cause, from the server console:**

```
[89622.033825] EXT4-fs error (device dm-1) in ext4_reserve_inode_write:6337: Journal has aborted
[89622.033842] EXT4-fs (dm-1): Remounting filesystem read-only
```

`dm-1` = `pve-root`, the OS volume on the 970. 89,622 s ≈ 25 h after the
2026-10-31 16:36 boot → **≈17:30 on 2026-11-01**. With root read-only, the kernel
still answered pings and TCP handshakes, but userspace services (pveproxy, sshd,
login) couldn't work. The console didn't respond to the keyboard either.

**Recovery.** Hard power-off at the PSU rocker (safe: the filesystem was already
read-only, nothing in flight) → booted fine, ext4 journal replayed.

**Evidence gathered after reboot:**

- 970 SMART: Critical Warning `0x00`, Available Spare 100%, Percentage Used 1%,
  **Media and Data Integrity Errors 0**, **Error Information Log Entries 0**,
  Power On Hours 13,973, Unsafe Shutdowns 438 (mostly desktop history).
  → **The drive itself is healthy and never logged an error.**
- `tune2fs -l /dev/mapper/pve-root`: **Filesystem state: clean.**
- Previous boot's kernel log (`journalctl -b -1 -k`): only boot-time lines; nothing
  recorded near the failure — once the disk dropped out, the log couldn't be saved.
- `ACPI FADT declares the system doesn't support PCIe ASPM` → PCIe ASPM is already
  off on this board; not a suspect.

**Diagnosis (⚠️ probable, not proven):** Samsung NVMe **APST** (Autonomous Power
State Transitions) — known on Linux to put some Samsung drives into a deep sleep
they fail to wake from, so the controller drops off and in-flight writes fail.
Fits: healthy drive, empty drive error log, failure after ~25 h mostly idle.
Alternatives not excluded: a marginal M.2 seat (server was knocked 2026-10-29),
the ~13-year-old PSU.

**Fix applied (21:10).** Disabled APST deep states via kernel parameter:

```
# /etc/default/grub
GRUB_CMDLINE_LINUX_DEFAULT="quiet nvme_core.default_ps_max_latency_us=0"
update-grub   # found 7.0.14-26-pve (default) and 7.0.2-6-pve (fallback)
reboot
cat /sys/module/nvme_core/parameters/default_ps_max_latency_us   # → 0 ✓
```

Cost: ~1–2 W more at idle. Reversible: remove the parameter, `update-grub`, reboot.

**Verification plan.** It failed at ~25 h, so one quiet day proves little. Leave it
running **≥ 3 days** before calling it fixed. If it recurs with APST off, the next
suspects are the M.2 seating (reseat the 970) and the PSU.

Side findings: SSH works (`ssh root@192.168.1.169`) — the second way in when the
web UI is down. Running kernel confirmed **7.0.14-26-pve**. GRUB's menu includes
**memtest86+**, so future RAM tests need no USB stick.
